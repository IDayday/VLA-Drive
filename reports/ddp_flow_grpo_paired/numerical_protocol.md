# Numerical protocol and scope

The historical BF16 candidate chunk=1/2 test remains **FAIL**. Its original files in `../ddp_flow_grpo/` have not been changed. No threshold was chosen from a failing value. No chunk=2 request is internally converted to chunk=1.

This revision separates three questions:

1. **Mathematical objective/gradient:** CPU FP32 full original model, original BF16 checkpoint VALUES lifted exactly to FP32 (all989/995 source tensors are BF16), original images/processor, SDPA MATH, TF32 off, deterministic algorithms. G2 and G8, K10 each reuse the same saved G8 chain, old log-probabilities, signed diagnostic advantages, own-reference statistics, replay sample/seed and identical initial Adam state. G2 uses the first two saved candidates. No new candidate is sampled during chunk comparison or rerun. The signed probe is explicitly diagnostic; original official rewards/advantages are retained. Initial official F probe had all-equal advantages, so it alone cannot demonstrate nonzero policy gradients.
2. **Production reliability:** BF16 parameters, existing Qwen FlashAttention implementation, PyTorch2.5 CUDA FP32 autocast for the inherited history/projector/action path, FP32 probability, actual ZeRO-2 FP32 accumulation/communication, global scene batch16. The installed DeepSpeed0.16.9 parser accepts `data_types.grad_accum_dtype=fp32` and `communication_data_type=fp32`. This is parser evidence, not a successful CUDA buffer/update test. Actual activations/gradients/accumulation/partition/master/moment dtypes are instrumented. Production repeat, exact resume, optimizer update, fixed-noise ODE, checkpointing and world-size scaling gates must pass for BOTH original initializations. They are currently NOT_RUN on the new production profile because all GPUs are occupied.
3. **Chunk interchangeability:** FP32 equivalence does not certify BF16 chunk>=2. Current formal support is **none**. The proposed release is restricted to candidate_chunk1/transition_chunk1, only after independent production evidence. chunk>=2 requires explicit experimental diagnostic opt-in and is rejected for paired training.

Every tensor comparison records presence, max absolute error, relative L2, cosine, norm ratio, exact unequal-element count, counts outside tolerance, cumulative error histograms and first16 out-of-tolerance indices. All672 trainable tensors and language/history/projector/action/full-model summaries are retained, even when a parameter fails. Adam first/second moment summaries are separated from scalar step counters; whole-state relative L2 must not hide small moment errors behind those counters.

The historical elementwise criterion remains `abs(error) <= 2e-6 + 2e-3 * abs(reference)`. Results also expose relative update error and same-noise trajectory error, because passing an absolute threshold on tiny Adam updates alone proves little. Near-zero is RMS<=1e-12, independent of the acceptance tolerance; a typical1e-6 update is not treated as zero. Earlier reports used the tolerance for near-zero display: original reports are preserved, and presentation-only recomputation from their saved norms changes no allclose result.

Layer traces contain current condition, velocity, transition mean/std/elementwise log-probability, each candidate/step policy and KL loss, condition before/after projection and their gradients, full parameter gradients before and after clipping, actual CPU Adam moments/master/forward-weight updates, post-update same-chain probabilities, and fixed-noise ODE. New `committed_*` runs add the explicit velocity tensor trace absent from early exploratory runs. CPU optimizer evidence is never labelled DeepSpeed optimizer evidence.

The fixed-profile acceptance criteria have not been relaxed to salvage the old BF16 failure. Current code enforces the absence of release: no long run and no100-update paired stage until all required current-profile evidence exists. For exact same-profile interrupted/resumed training, comparison uses zero tolerance for every stored model/optimizer/master/scheduler/RNG/pending tensor. A full-model CPU Accelerate inner-epoch test is additional debugging evidence, not a replacement for the required CUDA/ZeRO-2 test.

Executable snapshots, entry-time source fingerprints, full original numerical JSON, independent gradient-scope JSON, raw artifact locations and source-vs-commit comparisons accompany the results. Early development results refer to their captured execution, not automatically to the final commit. Final committed-profile CPU reruns are separate; historical reports are not overwritten.
