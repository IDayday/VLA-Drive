# Frozen visual cache pilot

Only image embeddings, all three DeepStack tensors, three-view grid, full current token IDs/slots and MRoPE positions are stored. No LLM hidden states, GT, history embeddings or trainable query substitutions enter the cache. Per-step embedding lookup, history/foresight/action replacements and language forward/backward remain live. `FrozenVisionPayload` wraps the exact whitelist-only `_build_qwen_batch` boundary; it does not activate the old incompatible qwen_feature_cache path.

Identity includes ordered RGB bytes and instruction, actual frozen visual state hash, processor/tokenizer/transform/prompt identity, processor and visual source hashes, software/backend/precision, three views and no-augmentation identity. Each shard checksum is verified once per process and read by mmap; it is not hashed every optimizer step. Left-padding offsets and all foresight slots are preserved. A miss rejects rather than silently building the full dataset.

Measured P0 dimensions imply1728 visual tokens per scene ×2048 channels ×4bytes ×4 outputs =56,623,104 tensor bytes/scene (54MiB), before IDs/positions/grid/container overhead. The101,592-scene population would need about5.75TB before legal image deduplication. The shared output disk has about1.6–1.9TB available during this campaign, so full cache construction is neither authorized nor feasible here. The pilot is limited to64 real scenes in16 batched shards on the isolated worker's local disk. There is no compressed BF16 storage in this T0 pilot.

A future full cache decision must compare build cost plus random-read/H2D cost against saved visual work over remaining sample exposures. Training cache speed never represents deployment image-to-trajectory latency: deployment still needs the visual tower. OS caches are not globally flushed; first-process and repeated-process reads must not be mislabeled guaranteed disk-cold and RAM-hot measurements.

Actual64-scene online-write vs cache-read training: **PASS** on all8 ranks. Full final model/buffer and optimizer tensor hashes, all RNGs, IDs, two losses/gradient norms/LRs and data cursor match exactly. The first read followed an explicit file-specific DONTNEED advisory over the16 owned pilot shards; no global OS caches were flushed. See evidence/P5_EQUIVALENCE.json. A separate shuffled64-scene IO/H2D pilot measures8-rank cold-advised vs same-process warm reads; its times are not labeled full training speed.

Measured pilot storage:3,628,081,632 bytes in16 shards,56,688,775.5 bytes/unique scene. Full101592-scene capacity at that density is5.759TB (5.24TiB), before any demonstrably legal image deduplication. No full cache was built.

Eight-rank randomized IO: the first two32-scene batches after owned-file DONTNEED advice averaged1.06876s at the slowest rank (aggregate1.579GiB/s); checksum verification accounted for approximately0.964s. Six same-process warm batches averaged0.08504s (19.843GiB/s aggregate), with zero repeated checksum work. Combine plus H2D averaged74.73/75.70ms respectively. Storage is uncompressed, so decompression cost is zero. These are **IO-only** measurements with small sample counts, not a long training-throughput claim. The complete online-write versus read training comparison covers64 real scenes and two updates, for equality only.

The build pilot's process duration also includes model initialization, strict checkpoint loading, two complete backward/optimizer steps and full state fingerprinting. It is an upper bound for this small build attempt, not an isolated visual-cache construction rate. A dedicated full-build rate is UNTESTED. Break-even requires `remaining_exposures * (online exposed visual cost - cache exposed read/H2D cost) > build cost`, plus sufficient capacity. Inclusive visual CUDA time cannot simply be substituted for exposed cost under overlap. Since the precision/runtime route already reaches1.385s/update without any persistent cache, no full-cache speed or payback is claimed.

This small-sample build rate remains insufficient to guarantee a full-dataset rate under sustained IO.
