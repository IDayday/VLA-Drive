# Query Base runtime recommendation

The fastest completed 200-update measurement is `configs/iqe/performance_v2/combined_visual_bf16.yaml`. Its eight-A800, global32/micro4 slowest-rank-per-update statistics are **mean1.3850235s, p50 1.3831113s, p95 1.4246679s**, from189 unprofiled steady updates after10 warmup and one final pipeline-drain exclusion. Peak CUDA allocated/reserved memory is59.928/63.535GiB. All200 actual updates retain all four objectives, normal dropout/DropPath, repeat8 and the original100k learning-rate schedule starting at21000.

The current-round P0 is already optimized vision-ahead: mean2.7201651s, p50 2.6976132s, p95 2.9266801s over the same189-update protocol. The measured combination is1.964× faster, or49.08% less normal-update time. This is a same-data, same-eight-GPU comparison, not the historical S-series comparison. The old active Base's approximately4.1s is a separate live observation with different determinism/backend flags, not the controlled P0 denominator.

The combination enables fused AdamW, gradient-as-bucket-view with50MiB buckets, no language activation recomputation, and BF16 compute in the **frozen visual tower only**, retaining FP32 compute/output for its final merger and all three DeepStack mergers. All trainable parameters, gradients and Adam moments remain FP32; trainable-language/action autocast remains the existing BF16 policy. `find_unused_parameters=True` remains. The visual tower remains fully frozen/eval. This is **T1 numerical execution**, not bitwise-equivalent FP32 vision and not a new architecture or stochastic estimator.

The44.557s complete checkpoint stall is excluded from normal updates. At the original1000-update save cadence its measured amortized estimate is1.429581s/update, or22.384samples/s. The actual200-step diagnostic run paid a whole save at its end, plus startup/state verification; its end-to-end process cost is reported separately. It is incorrect to amortize that save as if the formal save cadence were200.

`combined_fp32.yaml` is the conservative precision alternative: identical FP32 visual/parameters to P0, with fused AdamW, bucket views and no recomputation. Its completed long timing and both variants' exact-resume certificates are recorded in the final evidence below. It still changes floating-point execution ordering (T1), so it is not labeled bitwise interchangeable with an arbitrary historical backend.

Candidates stopped after screening: native Query repeat1 had no material speed benefit and changes dropout sampling/gradient-estimator variance; all-visual BF16 exceeded the predeclared sampled gradient-error budget; BF16 execution weights with FP32-master Adam also exceeded that budget. None is silently included in this recommendation. The unsharded master experiment does not establish a ZeRO2 or original S-series backend result. Visual cache capacity is insufficient for a full build. Whole-pipeline compilation, static-graph DDP and token-compression architecture changes were not needed to obtain the measured gain.

No full Base was started or migrated. The live Base and the separately locked22k incremental starting point are unchanged. Replacement requires a verified checkpoint-safe pause, the final same-runtime numerical/resume certificate, an idle authorized eight-GPU host and actual checkpoint capacity. The supplied migration script refuses a still-running source Base; it sends no signal and changes no ACTIVE pointer. Runtime qualification makes no PDMS/convergence or formal deployment claim.
