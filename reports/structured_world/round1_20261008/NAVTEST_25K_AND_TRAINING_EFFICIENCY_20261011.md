## 非反向开销为何仍大

既有 16-update 完整 I/O profile 的稳态区间约为：

| 执行阶段 | 秒/更新 |
| --- | ---: |
| 当前 Qwen，包含输入准备与 vision | 0.68–0.72 |
| 原 FM 监督 | 0.06 |
| 新增真实 10 步 q0 proposal | 0.33–0.34 |
| 当前几何 | 0.17–0.18 |
| 逐时刻未来空间 | 0.113 |
| FGTR / 场景 head | 0.016 / 0.029 |
| 完整反向 | 1.59–1.60 |
| optimizer | 0.094 |
| rank-max 数据等待 | 0.0026–0.0029 |

这些是 CUDA current-stream 区间，包含主机提交间隙，部分父子区间和不同
stream 的工作重叠；不能严格相加作为 kernel-only 分账。
Qwen vision 已包含在 Qwen 总时间里，不能再加一次。

旧 S 普通训练的一次 FM forward 将 repeat8 扩展在 batch 上；它不在每次
更新中串行做 8 次或 10 次动作采样。新方法的 q0 则每步串行调用原 24 层、
1536 宽动作模型 10 次。no_grad 取消采样链反向，并不消除这些前向计算。
新增 proposal 和场景分支前向已带来约 0.65 秒成本。

两版执行精度也不同：旧 DeepSpeed 开启 BF16 模型副本并保留 FP32 optimizer
master/moments；新实现整体 FP32 参数、局部 BF16 autocast、FP32 几何/修正，
且梯度通信与若干 embedding/残差仍为 FP32。当前确定性开关也不同。
这些差异真实存在，但尚未做逐项配对 profile，不能给它们各自指定因果耗时。

## 尚可验证的优化

实际 G3 rank0 的 40 秒、50 Hz、非阻塞 py-spy 采样得到 1999 个主线程样本，
未暂停或修改原训练。Qwen 输入预处理调用中驻留 3.10 秒；vision 中
`modeling_qwen3_vl.py:227` 驻留 1.82 秒；targets `.to()` 中驻留 0.98 秒。
Python 主线程驻留包含异步计算等待，不是纯 CPU 时间或可直接节省的时间。
详细聚合见 `G3_TRAINING_HOST_STACK_20261011.json`。

优先候选是复用当前 vision grid 的整数 chunk lengths，避免每个视觉 attention
层对 Q/K/V 各执行一次相同 GPU `lengths.tolist()`。保留 attention 算子本身。
其次审查相同 Qwen 输入预处理能否提前准备，以及 pinned transfer 和 detached
诊断能否减少同步。预取已消除了大部分数据等待，增加 loader 数不能解释或
解决当前主要成本。常量缓存必须保持实际相机、变换、shape/device/dtype 身份。

这些候选尚未部署，收益未实测。必须验证相同输入、独立 RNG、输出/梯度、
optimizer 状态和连续/中断恢复边界，才可统一用于正式组。
已有 I/O 验收前向和 RNG 逐位一致，但不保证未来 CUDA 梯度/更新逐位一致；
严格梯度检查的既有失败已保留。改变参数/通信精度、attention backend、关闭
checkpoint 重算或减少 proposal 步数，均不能直接称无损。

当前训练与 Navtest 共享 GPU 的干扰已经移除；先前共卡曾使约 3.2 秒升至
9.2 秒。后续推理按动态空闲资源安排，保持正式训练吞吐。
