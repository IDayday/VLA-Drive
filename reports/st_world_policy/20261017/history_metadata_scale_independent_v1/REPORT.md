**FAIL_PACKED_READER_AND_LAYOUT_BINDING.** Two narrow fixes are needed before this new storage format is accepted. There is no evidence of changed history mathematics or silently dropped scenes in the tested valid path.

## HS-1: unsafe packed-file opening

`HistoryReader.read` first checks symlinks/resolved containment and then calls ordinary `Path.open('rb')`. A file can be replaced between those operations. The independent fixture replaces the checked shard with a symlink to a file outside the registered root at the actual opening boundary. With identical valid bytes, the reader successfully returns the external record. SHA validation proves contents, but does not enforce the claimed storage-root boundary.

The branch also lacks regular-file/single-link validation before reading. A FIFO reaches ordinary blocking `open` before size/hash validation. The fixture intercepts that call so it does not hang the test process; this is a control-flow reproduction, not an actual indefinite FIFO wait.

Repair only the packed reader: walk parent directories via no-follow descriptors, use nonblocking/no-follow opening of the leaf, validate a regular single-link file and its bounded byte range/version, and verify namespace identity around the read. Keep record SHA/schema/token/log checks and legacy file behavior. Do not weaken image or temporal contracts.

## HS-2: declared packed-only census can execute files layout

`prepare_causal_history.validate` checks the registration's packed layout and inventory strategy only when the parsed layout is packed. A default/files command with a registration declaring `record_layout=packed_log_v1` and `inventory_strategy=immutable_history_shards_v1` is accepted. The independent fixture reproduces this without a real registration or ledger. Require matching layout/strategy in both directions; preserve old files registrations which declare no packed strategy.

## Behavior verified

- The new writer retains record dictionaries, per-record SHA, selected manifest order, bounded shard splitting, immutable existing-shard comparison and retained orphan partials. It does not produce teacher tensors.
- Independent data consist of **256 schema-valid synthetic missing-history records**, generated by the existing history constructor. No actual images/logs are used. Both the old per-file reader and packed reader run the actual `validate_history_record`, with no validator mock, and return exactly equal values. Two groups of128 become two shards; a nontrivial manifest selection order is preserved.
- Rebuilding preserves exact shard bytes and inode identities. Corruption conflicts on resume and fails record reads. Invalid offsets, lengths and layout reject. A watched read requests exactly the selected record length rather than deserializing the full shard.
- AST comparison against the base finds `causal_frames`, `build_history_record`, `validate_history_record`, `crop_resize_affine`, `load_history_images`, and `collate_history_inputs` unchanged. This is a storage/reader change, not evidence of a new causal representation.
- The original20,000-entry limit remains. Cached census is restricted in the registration schema, runs again at publications/paths and at least every5 seconds; RSS/time/free-space checks remain. HS-2 still prevents claiming the declared layout is faithfully enforced end to end.

## Scale conclusions deliberately not made

This is synthetic code evidence, **not actual full-population PASS**. It does not measure raw image hashing, shared storage bandwidth, real full-history RSS or actual registration execution. Full manifest/current-request dictionaries remain in RAM; resume still reconstructs/revalidates all sources rather than cheaply skipping completed logs. Full-tree scans still occur per shard publication and periodically, so no strictly linear complexity is proven. The stated shard-count estimate assumes the byte limit does not split earlier;4096 is a hard bound, not a guarantee that every future population fits.

The previous history64 source and admission are separate and unaffected. The packed format needs its own corrected source identity, immutable registration and independent resource review before real construction. No actual ledger, claim, pilot, GPU, weight or original raw data was touched here.
