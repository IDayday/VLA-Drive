Future metadata finalize-existing implementation handoff
Base: 16ffebf8499f1b71cdec745b0b724dc08e07838f
Scope: metadata-only implementation and synthetic validation. NOT_RUN on real shards; independent reviews and Lead registration/dispatch remain required.

Problem and chosen adaptation
The diagnosed original SceneStream reads full log JSON at each log switch, three times. The immutable source set is 984972623 bytes; original source order forces 609.386354567 GiB for those three passes. The new entry reads each source shard once, hashes/parses those same bytes, validates its original semantic identity/registration/selected rows, and stores each canonical scene as a separate lossless zlib level-1 byte record. Three replays decompress one scene at a time in original source order. No shared cache service, disk spool, teacher tensor, source data change, or mathematics change is introduced.

Implementation files
- tools/st_world_policy/finalize_future_metadata.py: registration/lineage checks, source read lock and stat census, bounded compressed scene records, immutable publication, distinct completion validator.
- tools/st_world_policy/metadata_storage.py: future_finalization writer kind and finalize-existing command; existing flat-output census/publication guard remains enabled on every callback. No storage-policy/claim changes.
- tools/st_world_policy/teacher_provider.py: explicit new completion schema/name branch, calling the strict validator before unchanged original population/current-frame/order checks. Existing COMPLETE route remains unchanged.
- tests/st_world/test_finalize_future_metadata.py: small synthetic tests, including actual storage dispatcher.

Entry point
python -m tools.st_world_policy.finalize_future_metadata finalize-existing --registration <new signed registration> --registration-sha256 <SHA> --output <new root>
Actual use MUST be through the existing registered metadata_storage runner and Lead finite monitor. The entry never starts subprocesses or GPU work. It requires an existing distinct output directory owned by a new claim. Original source BUILD.lock is opened read-only and held with exclusive nonblocking flock; no old source/lock/RESULT contents are written. Existing partial output is retained and charged.

Registration contract
schema=st_future_metadata_finalization_registration_v1, phase=data_preparation, signed semantic identity; exact fields are enforced in _registration(). Bind new output_root, original source_root, original frozen source_code_root, source_plan/source_registration/source_terminal/source_ledger path+SHA pins, optional source_shard_receipts pin (required if old file exists), source_shards count/bytes/stat-census identity, explicit limits/max_cache_bytes/max_decoded_shard_bytes/max_row_bytes, and new implementation path+SHA pins. All GPU/teacher/training authorizations must be false.
shard_census(plan, original_root) returns the required stat-only source_shards record. Its snapshot includes exact log paths, device/inode/size/mtime/ctime; source directory must have exactly the expected JSON shard files, with bounded preserved partials. Runtime compares the initial and final census and the individual read snapshot. Lead may construct this receipt without reading shard contents.
implementation must contain this new module plus precisely METADATA_STORAGE_CALLBACK_DEPENDENCIES. It binds the new code separately from the original PLAN implementation pins. Current history source differs from old original pins, so original source_code_root MUST point to the original frozen writer tree; original PLAN is not rewritten or re-signed.

Actual old terminal lineage
The source terminal is the original st_full_future_build_invocation_v1 / FAILED_NO_AUTO_RETRY receipt, not a manufactured FAILED.json. Check no retry/training/scientific/teacher work, nonzero child return, cleanup.live_owned_remaining=0, exact role. The implementation reads only metadata and original code. It never opens original raw logs, image files, ego tensors or teacher caches. Their existing hashes/provenance are inherited from the immutable validated shards. source_with_pins still verifies original source index/partition/current selection control metadata.

Output identity and recovery
The new output root contains RAW_LOG_PROVENANCE.json, TEACHER_REQUESTS.json, SHARD_RECEIPTS.json and FINALIZATION_COMPLETE.json. Original registration identity and row contents/order remain fixed. New request header points honestly at the new ledger path, so request semantic identity may differ from the old-root expected identity. With an identical header and scene sequence, the existing serializer produces byte-identical atomic_json output; tests assert that exact property.
Completion schema is st_future_metadata_finalization_complete_v1, explicitly source_shards_reused=true and raw_log_deserialized=false for this invocation; it never writes old COMPLETE.json or claims original BUILD_COMPLETE. It pins finalization registration, original lineage, output file hashes, population, request identity, source census and costs. Publication is atomic through the existing temporary-file/fsync/guard path. Failure retains original shards/old failure evidence and every new partial; retry recomputes from those same immutable shards. Existing completed output must match bytes, and completion retry ignores only invocation-dependent cost/identity while preserving the original receipt bytes.
The downstream validator verifies the signed new receipt, its registration and original terminal/PLAN/registration lineage, output ledger/shard receipt hashes and exact paths/coverage, then matches the caller's already-verified request SHA/identity/header/count. Existing PROFILE full-population checks continue to stream selected/current/future records and reject order/first-frame changes.

Resource contract and limits
One reader; logical reads <=16 GiB implementation ceiling, rate <=64 MiB/s, wall <=14400 s, RSS <=4 GiB per original PreparationBudget ceilings. A concrete new admission may choose tighter limits. New output (including partials) <=2 GiB, preserving the old source claim separately; do not copy 984 MB of source shards.
Compressed cache <=512 MiB including bytes objects, token keys, tuple/length/digest objects and actual dict capacity, with conservative dict-growth and one-row space checked BEFORE insertion/compression. Row JSON/decompression <=64 KiB; object size and RSS are checked around each row.
Before reading/parsing each whole shard: file <=64 MiB, 64*file_size <= explicit decoded-workspace allowance, and peak-RSS+67*file_size <= RSS limit. Actual recursive decoded object size is then checked against that allowance. These are conservative engineering estimates, not a mathematical allocator guarantee; the mandatory independent finite RSS monitor remains authoritative. Max decoded-workspace allowance <=1 GiB. The prior stat evidence's largest real shard is 10413165 bytes, so 768 MiB is a compatible proposed allowance; no actual large-shard decode was run here.
Decompression uses decompressobj.decompress(blob, max_row_bytes+1); requires eof, no unused_data, no unconsumed_tail, exact original length, and canonical-byte SHA. No unbounded decompress/flush fallback. Corrupt/truncated/trailing/compression-bomb records fail before completion.
All known metadata input reads and output writes use existing pacing/budget hooks. Source shard bytes are preflighted as a whole before processing and rechecked after source-control reads. Source shard SHA and JSON decode share the one file read. validate_ledger reads its file ONCE then hashes/parses the same data, so each call is charged one size (old builder reserved two); final request parser and final request SHA are separate reads and charged separately. Output census remains fresh on every guard callback and before every actual creation/publication; this flat new root does not need a cached census strategy.

Evidence card
Design type: local execution optimization, not a new model or supervision method.
Local reference: original prepare_future_metadata.py SceneStream, row_document_identity, write_row_document, write_chunks, and st_world_future_provenance.py validate_ledger at fixed base/frozen original source.
Primary documentation: https://docs.python.org/3/library/zlib.html#zlib.Decompress.decompress ; https://docs.python.org/3/library/zlib.html#zlib.Decompress.unconsumed_tail ; https://docs.python.org/3/library/zlib.html#zlib.Decompress.eof . Official docs explain that nonzero max_length bounds output, tails retain unconsumed input, and eof distinguishes truncation. Local installed CPython 3.9 zlib.decompress docstring was read; build zlib 1.2.13 / runtime 1.3.1, and actual bounded API behavior is tested. Level 1 is an engineering speed/space choice; no full-scale compression ratio or ETA is claimed.
Acceptance: byte/identity parity for fixed header; shuffled-log original order; one source-shard read; no raw/image/tensor opens; bounded corruption failure; no completion on budget/identity/census/guard failure; preserved partials and deterministic resumed output; strict new consumer path and unchanged legacy path.
